# Правила проекта

## Архитектура

- Хендлер — транспорт; usecase — сценарий; сервис — общая бизнес-логика; репозиторий — хранение данных.
- Вызовы направлены вниз: хендлер → usecase → сервис → репозиторий; вызовы верхних и соседних компонентов запрещены.
- Домен не зависит от транспорта, БД и сгенерированного API.
- В бизнес-коде использовать доменные и прикладные модели, не HTTP DTO и записи БД.
- Маппинг выполнять на границах: API ↔ домен — в транспортном маппере, записи БД ↔ домен — в адаптере в репозитории. Ошибки преобразования возвращать вызывающему коду.
- Узкие интерфейсы зависимостей объявляет потребитель.

## Работа с кодом

- Комментарии не добавлять, кроме AAA в тестах (`// arrange`, `// act`, `// assert`) и при какой-то очень сложной логике в коде (в таком случае можно добавить в качестве исключения).
- Тесты добавлять и расширять только по запросу или в рамках согласованной тестовой части задачи, не ради покрытия.
- Соблюдать идиомы Go и стиль проекта; ошибки возвращать с сохранением причины через `%w`.
- Генерируемый код руками не менять: править контракт или настройки генератора.
- Не менять контракты, архитектуру и пользовательские правки вне согласованной задачи; ветки, коммиты и push — только по запросу.
- Сообщения коммитов писать на русском в прошедшем времени («Добавил», «Исправил»), а независимые логические изменения оформлять отдельными коммитами.
- Проверки выбирать соразмерно изменениям; для документации не запускать тесты и сборку.
- Документация — на русском, технические имена — на английском.
